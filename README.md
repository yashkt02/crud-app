# Everyday Expense Tracker

The application is split into three independently runnable Spring Boot services:

- `property-crud-app/`: expense CRUD API and browser UI (port 8080). Publishes expense changes to Kafka.
- `property-crud-app/auth-service/`: account registration, login, JWT issuance, and admin user listing (port 8081).
- `property-crud-app/summary-service/`: Kafka consumer and category/month summary API (port 8082).

## Run the full stack locally

Install Docker Desktop and start its Linux container engine. From the project root, start the full stack with:

```powershell
docker compose up --build
```

The first build downloads the service dependencies and container images. Open [http://localhost:8080](http://localhost:8080) when startup finishes. Compose starts the expense UI/API, auth service, summary service, Kafka, and a dedicated MySQL database. MySQL is exposed on host port `3307`, so it does not conflict with a local MySQL server on `3306`. The app services use the Compose network and do not need local Kafka or MySQL credentials.

The local admin account is `admin` with password `yash1234`. This is a local-only convenience password; change it by setting `ADMIN_PASSWORD` before starting Compose, and never use this default in a shared or deployed environment. Set `JWT_SECRET`, `ADMIN_PASSWORD`, `MYSQL_ROOT_PASSWORD`, and `MYSQL_APP_PASSWORD` to private values for any shared environment. Demo user accounts are not created unless `DEMO_USERS` is explicitly set. Data is retained in Compose volumes. Stop the services with `Ctrl+C`, then run `docker compose down`; `docker compose down -v` also deletes the local database and account data.

### Deploy the full stack to Render

The root `render.yaml` defines the Expense, Auth, and Summary web services plus private MySQL and Kafka services. It uses persistent disks for Auth accounts, MySQL data, and Kafka logs. Private services and persistent disks require paid Render resources; review the Blueprint's estimated cost before confirming creation. During the first Blueprint setup, Render prompts for `ADMIN_PASSWORD`; choose a private password there. JWT and MySQL credentials are generated by Render and scoped to the services that need them. Browser requests to Auth and Summary go through the Expense service's same-origin `/gateway` routes, so no public backend URLs or permissive CORS rules are needed.

To run a single service outside Compose, install JDK 17 or newer and Maven 3.6.3 or newer, and configure its dependencies as described below.

For local API/UI testing without Docker or MySQL credentials, start Summary Service with the `local` profile. This uses a separate H2 file database and disables the Kafka consumer; category/month summaries will not receive expense events unless Kafka is running. The standard profile and Compose deployment continue to use MySQL and Kafka.

When running the services directly on the host without Kafka, start the expense service with the `local` profile as well. This disables only expense event publication so create, update, and delete remain usable; event-based summary aggregation requires Kafka and is available with the standard profile or Compose stack.

## Run on Windows

In each service terminal, set the same JWT secret and Kafka address. Use a randomly generated secret with at least 32 bytes. Configure the admin credentials in the auth-service terminal.

```powershell
$env:JWT_SECRET = "paste-the-same-random-secret-here"
$env:KAFKA_BOOTSTRAP_SERVERS = "localhost:9092"
```

Auth-service terminal:

```powershell
$env:ADMIN_USERNAME = "admin"
$env:ADMIN_PASSWORD = "choose-a-strong-password"
cd auth-service
mvn spring-boot:run
```

Summary-service terminal:

```powershell
$env:SUMMARY_DB_URL = "jdbc:mysql://localhost:3306/expense_tracker?createDatabaseIfNotExist=true"
$env:SUMMARY_DB_USERNAME = "root"
$env:SUMMARY_DB_PASSWORD = "your-local-mysql-password"
$env:AUTH_SERVICE_URL = "http://localhost:8081"
cd summary-service
mvn spring-boot:run
```

Expense-service terminal (from this directory):

```powershell
mvn spring-boot:run
```

Open [http://localhost:8080](http://localhost:8080). Register a regular USER account or sign in with the configured admin. The admin can access summaries; USER tokens can perform expense CRUD only.

## APIs

Auth service:

- `POST /api/auth/register` with `{"username":"...","password":"at-least-8-chars"}` creates a USER and returns a JWT.
- `POST /api/auth/login` returns a JWT.
- `GET /api/admin/users` lists usernames and roles (ADMIN only).
- `GET /api/users` lists usernames and roles to an authenticated USER or ADMIN; credentials are never returned.

Expense service (Bearer JWT required; USER or ADMIN):

- `GET|POST /api/expenses`
- `GET|PUT|DELETE /api/expenses/{id}`

Summary service category reports (Bearer ADMIN JWT required):

- `GET /api/summaries/categories` optionally accepts `?month=2025-03`.
- `GET /api/summaries/monthly?month=2025-03` returns the monthly total, count, and category totals.

Lend & Borrow (Bearer USER or ADMIN JWT required):

- `GET /api/lend-borrow/users` lists registered peers, excluding the signed-in user.
- `POST /api/lend-borrow/requests` creates a `PENDING` request with `recipientUsername`, `direction` (`LEND` or `BORROW`), `amount`, and optional `description`.
- `GET /api/lend-borrow/requests/sent` and `GET /api/lend-borrow/requests/received` list the caller's requests.
- `POST /api/lend-borrow/requests/{id}/decision` accepts `{"status":"APPROVE"}` or `{"status":"REJECT"}`; only the intended recipient can decide, once.
- `GET /api/lend-borrow/overview` returns lent/borrowed totals, outstanding balances, pending sent/received requests, and confirmed history for the caller.

Only approval changes a request to `APPROVED` and includes that same request ID in both users' history. Rejected and pending requests do not affect totals. No repayment is implied or recorded, so outstanding-to-receive/pay equals approved lending/borrowing totals until a separate repayment feature is implemented.

Expense mutations publish keyed `UPSERT` and `DELETE` events to Kafka topic `expense-events`; the summary consumer replaces state by expense ID to avoid counting updates twice.

## Data and testing

Expense records remain in-memory and reset when the expense service restarts. Auth accounts use their configured auth database. Summary expense aggregates are in-memory and rebuild from retained Kafka events; lend/borrow requests are stored in the Summary Service MySQL database using `schema.sql`.

Run each app's tests from its directory with `mvn test`. The expense CRUD API retains its validation rules: amount must be positive and the date cannot be in the future.
